PART I — PRODUCT REQUIREMENTS DOCUMENT (PRD)
============================================================

1. PRODUCT OVERVIEW

ProtoHub is an AI-powered collaborative learning platform connecting students, teachers, mentors, and industry professionals in one unified workspace. The MVP focuses on learning through real-world projects: users can discover collaborators and mentors, create and manage projects, communicate, receive AI-assisted guidance, and build a professional portfolio.

2. VISION

To become a global platform where learning happens through collaboration, mentorship, and real-world project experience.

3. MISSION

Help learners transform knowledge into practical skills by connecting them with experienced people and collaborative project opportunities, supported by AI-powered tools.

4. PROBLEM STATEMENT

• Students struggle to find reliable mentors and project teammates beyond their immediate college or social network.
• Project work is fragmented across chat, task-management, documentation, file-storage, and code platforms.
• Students often lack timely expert guidance while building projects.
• Teachers and professionals lack a focused environment for mentoring and project collaboration.
• Traditional learning platforms emphasize content consumption rather than learning by building.

5. PRODUCT GOAL

Create a focused MVP that makes ProtoHub useful for one core journey: a student discovers a project or mentor, forms or joins a team, collaborates in a project workspace, receives mentorship, uses AI assistance, and completes work that can strengthen their portfolio.

6. TARGET USERS

• Students: learners seeking practical experience, teammates, mentors, and portfolio projects.
• Teachers: educators who want to guide students and participate in projects.
• Industry Professionals: experienced people willing to mentor, review, or collaborate with learners.
• Administrators: platform operators responsible for moderation and system management.

7. CORE VALUE PROPOSITION

ProtoHub is not simply another course platform or social network. It combines mentorship, project collaboration, communication, project management, and AI assistance around a single project-centered experience.

10. PRODUCT PRINCIPLES

• Project-first: the project workspace is the core product experience.
• MVP-first: avoid building courses, payments, recruiters, video calls, and other expansion features before validating the core.
• Trust and safety: profiles, requests, reporting/moderation, and permissions must be designed carefully.
• Useful AI: AI should be contextual to projects and learning rather than being an unrelated generic chatbot.
• Scalable foundations: data and module boundaries should support later expansion.

============================================================
PART II — SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
============================================================

1. PURPOSE

This SRS defines the functional, non-functional, architectural, security, data, API, and implementation requirements for the ProtoHub MVP.

2. SCOPE

The MVP is a web application using a Next.js frontend and NestJS modular-monolith backend, backed by PostgreSQL through Prisma, with Socket.IO for real-time communication, Cloudinary for file storage, and an external AI provider for the AI assistant.

3. USER ROLES AND PERMISSIONS

Student:
Profile, discover, create/join projects, mentorship requests, chat, tasks, AI.

Teacher:
Professional profile, mentorship, project collaboration, chat, project guidance.

Professional:
Professional profile, mentorship, project collaboration, chat, project guidance.

Admin:
Moderation, user/project management, reports, platform administration.

4. FUNCTIONAL REQUIREMENTS

FR-AUTH — The system shall support registration, login, logout, password reset, email verification, session/token management, and role-based authorization.

FR-PROFILE — The system shall allow users to create and edit professional profiles containing identity, bio, education, experience, skills, interests, and portfolio information.

FR-DISCOVERY — The system shall allow users to search and filter users, mentors, and projects.

FR-PROJECT — The system shall allow authorized users to create, update, view, archive, and manage projects.

FR-WORKSPACE — Each project shall have an associated workspace for members, tasks, files, discussion, activity, and project-context AI.

FR-MEMBERS — Project owners shall be able to invite/remove members according to project permissions; users shall be able to join projects where permitted.

FR-MENTOR — Students shall be able to request mentorship and mentors shall be able to accept, reject, or otherwise manage requests.

FR-CHAT — The system shall support direct and project conversations with persistent message history and real-time delivery.

FR-TASK — Authorized project members shall be able to create, assign, prioritize, update, and complete tasks.

FR-NOTIFY — The system shall create notifications for defined collaboration and system events and maintain read/unread state.

FR-AI — The system shall provide project-related AI assistance and persist AI conversation history where permitted.

FR-FILES — The system shall support secure file uploads through external object/media storage and persist metadata/URLs.

FR-ADMIN — Administrators shall be able to moderate users, projects, and platform reports.

5. NON-FUNCTIONAL REQUIREMENTS

• Performance: optimize common API responses and database queries; use pagination for list endpoints and indexes for high-frequency queries.
• Scalability: modular backend boundaries must permit future extraction into services if growth requires it.
• Security: passwords must be strongly hashed; secrets must be environment-managed; inputs validated; authorization enforced server-side.
• Availability: application should be deployable using managed cloud infrastructure with health checks and automated deployment.
• Reliability: database constraints and transactions must protect relationship integrity.
• Accessibility: UI should follow accessible semantic HTML, keyboard navigation, labels, focus states, and contrast requirements.
• Responsiveness: core workflows must work across desktop, tablet, and mobile viewport sizes.
• Observability: structured server logs, error handling, and basic health endpoints are required.

7. BACKEND MODULE RULES

• Controllers handle transport concerns only.
• Services contain business logic.
• Repositories/data-access abstractions isolate persistence logic where useful.
• DTOs validate and describe input contracts.
• Guards enforce authentication and authorization.
• Shared utilities must remain generic and not contain feature-specific business logic.
• Modules should expose only the interfaces required by other modules.

8. DATABASE REQUIREMENTS

Core entities for the MVP include:
User, Profile, Skill, UserSkill, Project, ProjectMember, Workspace, Task, Conversation, ConversationMember, Message, MentorshipRequest, Notification, AIConversation, AIMessage, and File metadata where implemented.

• Use UUID primary keys.
• Use foreign keys and explicit relationship constraints.
• Use createdAt/updatedAt consistently.
• Use indexes on authentication identifiers and frequent lookup/filter fields.
• Use uniqueness constraints for email and other identifiers that must be unique.
• Use transactional operations for multi-record state changes such as accepting mentorship or project membership operations.

11. FILE HANDLING

• Files should be uploaded to managed external storage rather than stored directly in PostgreSQL.
• The backend should validate file metadata and authorization before issuing/accepting uploads.
• Database records should store file owner, project/workspace association, original name, MIME type, size, storage key/URL, and timestamps.
• Access to private files must be authorization-controlled.

12. AI REQUIREMENTS

• AI requests must be routed through the backend; provider secrets must never be exposed to the browser.
• Project context should be supplied only when the requesting user has access to the project.
• Conversation history should be persisted where enabled.
• Prompts should be versionable/configurable rather than scattered through frontend code.
• Implement rate limits and usage controls before public launch.

13. SECURITY REQUIREMENTS

• Passwords must use Argon2id or an equivalently strong password hashing scheme.
• Use secure, HTTP-only cookies for refresh/session tokens where appropriate.
• Use short-lived access tokens.
• Apply RBAC on every protected server operation.
• Validate request bodies, params, and query strings.
• Configure CORS explicitly.
• Use security headers and rate limiting.
• Do not log passwords, tokens, API keys, or sensitive user data.
• Use environment variables for secrets and provide a safe .env.example.

14. FRONTEND REQUIREMENTS

• Use Next.js App Router and TypeScript.
• Use a consistent design system based on shadcn/ui and Tailwind CSS.
• Use TanStack Query for server state.
• Use React Hook Form + Zod for complex forms.
• Implement loading, empty, error, and success states for every major data-driven page.
• Use route protection for authenticated pages.
• Keep components reusable and feature-oriented.

16. TESTING REQUIREMENTS

• Unit tests for important business rules and services.
• Integration tests for database-backed modules.
• API/e2e tests for authentication, projects, mentorship, and core collaboration workflows.
• Frontend tests for critical forms and user journeys where appropriate.
• Manual smoke testing before each release.
• Test authorization failures, not only successful requests.

17. DEPLOYMENT REQUIREMENTS

• Frontend deployable to Vercel.
• Backend deployable to Railway or equivalent container/Node platform.
• PostgreSQL deployable on Neon or equivalent managed PostgreSQL.
• Production environment must use separate secrets and database credentials.
• CI should run linting, type checking, tests, and build verification.
• Database migrations must be version-controlled.

18. MVP ACCEPTANCE CRITERIA

• A new student can register, verify/access an account, and complete a profile.
• A user can discover mentors and projects.
• A student can create a project and invite/join members according to permissions.
• Project members can access a shared workspace and manage tasks.
• Users can create direct/project conversations and exchange persistent messages.
• A student can submit a mentorship request and a mentor can accept/reject it.
• Users receive relevant notifications.
• An authorized user can use the AI assistant with project context.
• Unauthorized users cannot access private project data or conversations.
• The MVP can be deployed from a clean environment using documented setup instructions.

Sprint 1 → Repository + PostgreSQL + Prisma + database + seed
Sprint 2 → Auth + Users + Profiles + RBAC
Sprint 3 → Projects + Members + Workspace + Tasks

20. DEFINITION OF DONE

• Feature requirements are implemented and documented.
• Authorization rules are enforced server-side.
• Database migrations are committed.
• Validation and error handling are implemented.
• Tests cover critical behavior.
• UI has loading, empty, error, and success states.
• No secrets are committed.
• Lint/type-check/build pass.
• Feature is manually smoke-tested.
• Documentation is updated.
