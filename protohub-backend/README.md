# ProtoHub Backend

NestJS (modular monolith) + PostgreSQL + Prisma API for ProtoHub.

## Setup

```bash
npm install
cp .env.example .env
# fill in DATABASE_URL (Neon or local Postgres), JWT_ACCESS_SECRET, etc.

npx prisma generate
npx prisma migrate deploy    # applies prisma/migrations/0001_init
npm run prisma:seed          # optional — realistic demo data

npm run start:dev            # http://localhost:4000/api/v1
```

**This has not been run against a live database yet** — the sandbox this was built in couldn't reach `binaries.prisma.sh` or a real Postgres instance. The migration SQL was hand-verified against `schema.prisma` field-by-field rather than generated by the CLI. Run `npx prisma migrate deploy` yourself and treat that as the real first integration test.

## Architecture

- **Modular monolith**: Controller → Service → Repository → Prisma → PostgreSQL, one module per domain concept.
- **Two authorization layers, deliberately separate**: global `UserRole` RBAC (`RolesGuard`) for platform-wide permissions, and project-scoped `ProjectMemberRole` checks (`ProjectsService.assertProjectRole`) for who can do what inside one project. A `STUDENT` can own a project — these are genuinely different axes.
- **Event bus for cross-module side effects** (`@nestjs/event-emitter`): e.g. when a join request is accepted, `ProjectsService` emits `project.member.joined`; `Chat` and `Notifications` react independently. No module imports another's business logic to cause a side effect in it.
