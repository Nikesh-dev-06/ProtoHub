PROTOHUB — COMPLETE UI/UX SPECIFICATION
Version 1.0 — MVP

This document is the authoritative UI/UX specification for the ProtoHub MVP.
The PRD/SRS defines WHAT ProtoHub does; this document defines HOW ProtoHub looks and behaves.

1. DESIGN DIRECTION

ProtoHub should feel professional, youthful, technical, collaborative, and trustworthy.

Design inspiration:
- Linear: clean project/work management
- Notion: flexible workspace feel
- GitHub: developer credibility
- Slack: communication
- Vercel: modern SaaS quality

Do not copy these products. Create an original ProtoHub identity.

Avoid childish education graphics, excessive gradients, excessive glassmorphism, generic neon AI aesthetics, cluttered dashboards, excessive rounded cards, and unnecessary animation.

23. EMPTY STATES

Every page must have intentional empty states.

Example:
"No projects yet."
"Your next great project could start here."

Actions:
- Create Project
- Discover Projects

Never leave a page blank.

24. LOADING STATES

Use skeleton loaders for content-heavy pages.
Avoid full-screen spinners unless absolutely necessary.
Skeletons should resemble the final layout.

25. ERROR STATES

Example:
"Something went wrong."
"We couldn't load this project."
[Try Again]

Never expose stack traces, database errors, or internal technical details.

26. TOASTS

Use subtle toast notifications.

Success:
- Project created successfully
- Mentorship request sent
- Task updated

Error:
"Unable to save changes. Please try again."

Toasts should not block the user.

27. MODALS

Use modals for:
- Delete confirmations

- Small focused forms

Prefer dedicated pages for:
- Create project
- Profile editing
- Settings
- AI
- Project workspace

28. TYPOGRAPHY

Recommended:
Inter or equivalent modern sans-serif.

Sizes:
- Page title: 28–32px
- Section title: 20–24px
- Card title: 15–17px
- Body: 14–16px
- Metadata: 12–13px

29. SPACING

Use an 8px spacing system:
4, 8, 12, 16, 24, 32, 40, 48, 64px.

Cards generally use 20–24px internal padding.

30. BORDERS

Use subtle borders.
Avoid heavy outlines.
Cards should feel structured rather than boxed in.

31. BORDER RADIUS

Recommended:
- Buttons: 8px
- Inputs: 8px
- Cards: 10–12px
- Dialogs: 12–16px

Do not make every element pill-shaped.
Use pills mainly for tags, statuses, and filters.

32. COLOR SYSTEM

Use a mostly neutral interface.

Semantic design tokens:
- Background
- Foreground
- Muted
- Border
- Primary
- Secondary
- Success
- Warning
- Destructive
- Info

Use a distinctive but restrained ProtoHub primary color.

Do not use rainbow UI.

Status colors:
- Success: green family
- Warning: amber family
- Error: red family
- Info: blue family

Support complete dark mode.

34. FORMS

Every form field should have:
- Label
- Input/control
- Helper text when useful
- Validation
- Error message

Example:
Project name *

"Give your project a clear, memorable name."

Validation:
"Project name is required."

35. RESPONSIVE BEHAVIOR

Desktop:
- Persistent sidebar
- Top bar
- Multi-column layouts where appropriate

Tablet:
- Collapsible sidebar
- Reduced multi-column layouts

Mobile:
Top header:
- Menu
- ProtoHub
- Notifications

Bottom navigation:
- Home
- Discover
- Projects
- Messages
- Profile

Project workspace:
Use horizontal scrolling tabs or another mobile-friendly navigation control.

36. ACCESSIBILITY

Every interactive element must support:
- Keyboard interaction
- Visible focus state
- Accessible label
- Sufficient contrast
- Semantic HTML

Images require meaningful alt text.
Icon-only buttons require accessible labels.
Never communicate status through color alone.

37. ANIMATION

Animations must be subtle and fast.

Appropriate:
- Page transitions
- Dropdowns
- Dialogs
- Hover feedback
- Toast appearance
- Task movement

Avoid:
- Constant floating animations
- Excessive bouncing
- Unnecessary parallax
- Slow transitions

The UI should feel fast.

38. MICROINTERACTIONS

Examples:
Task: Unchecked -> Checked
Mentorship: Request -> Connected
Project creation: Create -> Creating... -> Created
Message: Sending... -> Delivered

Use microinteractions to make state changes clear without becoming distracting.

39. PROJECT STATUS

Statuses:
- Planning
- Active
- Completed
- Archived

Each status should have an icon, label, and semantic visual treatment.

40. PROJECT VISIBILITY

Options:
- Public
- Private
- Invite Only

Show a visibility icon next to project status where useful.

1. What am I working on?

43. ANTIGRAVITY IMPLEMENTATION INSTRUCTION

Read:
docs/ProtoHub_PRD_SRS.txt
docs/ProtoHub_UI_UX_Specification.txt

The PRD/SRS defines WHAT ProtoHub must do.
This UI/UX specification defines HOW ProtoHub must look and behave.

Treat both documents as authoritative project requirements.

Build the complete ProtoHub frontend according to both documents.

Do not create a generic dashboard template.
Do not invent random pages.
Do not simplify specified pages without explaining why.

Implement:
- Complete navigation
- Page hierarchy
- Layouts
- Components
- Design system
- Responsive behavior
- Accessibility
- Forms
- Loading states
- Empty states
- Error states
- Success states
- Notifications
- Modals
- Drawers
- Tabs
- Filters
- Project workspace
- Chat
- AI interface
- Profiles
- Mentor discovery
- Project discovery
- Dashboard
- Settings
- Admin interface

Use existing backend APIs when available.

If an API is not implemented yet:
- Create a clean typed API abstraction.
- Use realistic development data only where necessary for UI development.
- Keep mock data separate from production data.
- Do not permanently hardcode mock data into UI components.

Create reusable components and a consistent ProtoHub design system.

Before implementation:
1. Inspect the existing frontend.
2. Inspect backend/API contracts.
3. Inspect project structure.
4. Read both specification documents completely.
5. Create a frontend implementation plan.
6. Identify missing APIs required by the UI.
7. Implement incrementally.

For every page verify:
- Desktop layout
- Tablet layout
- Mobile layout
- Loading state
- Empty state
- Error state
- Success state
- Permission state
- Accessibility
- Keyboard navigation
- Responsive navigation
- Form validation
- API error handling

A page is not complete merely because it renders.

A page is complete only when its interactions, states, responsive behavior, accessibility, and API integration are implemented.

Start by auditing the repository and creating the frontend implementation plan.
Do not begin by generating random UI code.
